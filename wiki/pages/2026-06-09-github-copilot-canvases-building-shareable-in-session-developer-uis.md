## TL;DR

> GitHub Copilot canvases are described as code-defined, in-session interfaces that combine project visibility with agent-triggered actions. They matter because teams can turn repetitive prompt-based workflows into reusable, reviewable tools shared through repositories or gists.

## Key Takeaways

1. Treat a canvas as versioned team tooling: its code can be reviewed, committed to a repository, shared as a gist, and reused across sessions.
2. Use canvases for repeated workflows where a purpose-built interface is faster and more discoverable than repeatedly writing natural-language prompts.
3. Separate the design into project state, rendered UI, agent-triggered actions, and distribution or configuration.
4. Combine visibility and control in one surface—for example, show worktree divergence from `main`, open associated sessions, and request cleanup of orphaned worktrees.
5. Define each interaction with three parts: the user event, the command or prompt sent to the agent, and the expected UI refresh.
6. Require confirmation for destructive actions such as deleting local worktrees, especially when generalizing a canvas for team use.
7. Replace repository-specific assumptions with configuration options such as the default branch, sort metric, and destructive-action policy.

## Overview

This lesson explains the GitHub Copilot App "canvas" concept described in the source: lightweight, code-defined interfaces that run inside a Copilot session and let engineers create custom views and controls for their development workflow. The example shown is a session browser that visualizes git worktrees, shows how far each has diverged from main, and lets the user jump to or clean up sessions directly from the canvas.

Why this matters is that it shifts Copilot from being only a chat-based assistant into something closer to a programmable developer workspace. Engineers who manage multiple branches, worktrees, tasks, or local environments can build narrow, task-specific UIs, check them into a repository, and share them with a team so the workflow becomes reproducible instead of living only in one person's prompts.

## Key Concepts

- **Canvas as code**: A canvas is described as code that defines a custom interface inside a GitHub Copilot session. Because it is just code, it can be versioned, reviewed, checked into a repository, or shared as a gist and reused by others.
- **In-session custom UI**: Instead of relying only on chat prompts or a sidebar, a canvas provides a purpose-built interface tailored to a workflow. In the example, the UI acts as a visual session browser for project worktrees and branch state.
- **Two-way interaction**: The transcript highlights that canvases are not only read-only dashboards. User actions in the UI can trigger navigation to another session or send prompts back to the Copilot agent, which then performs operations and updates the UI.
- **Git worktree awareness**: The demonstrated canvas organizes sessions by git worktrees and compares them to main. This makes branch divergence and stale or orphaned worktrees visible, which is useful when many parallel tasks are active.
- **Workflow automation through agent actions**: The UI can initiate operational tasks such as deleting orphaned worktrees from local disk. This turns the canvas into both an observability layer and a control plane for repetitive development tasks.
- **Team portability**: Since canvases can be committed to a repo or distributed through a gist, a team can standardize internal tooling without building a full standalone application. The same interface can be installed into multiple Copilot sessions and reused across projects.

## How It Works

The source describes canvases as embedded, programmable interfaces that live inside the GitHub Copilot App. Conceptually, a canvas sits between three things:

1. **The developer's local/project state** — sessions, worktrees, branches, diffs, or other project metadata.
2. **A rendered UI** — a visual component that presents that state in a more useful way than raw text.
3. **The Copilot agent** — which can receive commands generated by UI interactions and execute workflow steps.

In the example workflow, the canvas is acting as a specialized dashboard for a repository with multiple active sessions. The data model appears to include:

- a list of sessions associated with the current project
- each session's corresponding worktree
- divergence from `main`, measured either by commit distance or file changes
- a classification of active versus orphaned worktrees

The user can then switch how divergence is displayed, likely by toggling between metrics such as commit count and file-change count. This is a useful design pattern: the canvas exposes one project state through multiple visual interpretations depending on the question being asked.

A plausible interaction flow from the transcript looks like this:

- The canvas loads project/session metadata.
- It renders each worktree/session in a visual browser.
- The user clicks an item.
- That click either:
  - navigates directly to the corresponding Copilot session, or
  - sends an instruction back to the agent to perform an operation, such as deleting an orphaned worktree.
- After the action completes, the canvas refreshes and redraws the state.

That means canvases are effectively **stateful UI wrappers around agent-capable workflows**. They do not replace the agent; they structure and constrain how the user invokes it.

From an engineering perspective, this matters because natural-language interaction is flexible but often inefficient for repeated tasks. A canvas can encode recurring operations into explicit controls:

- "show me all worktrees sorted by divergence"
- "jump into this session"
- "clean up this orphaned worktree"
- "refresh the visualization"

This approach has several practical advantages:

- **Discoverability:** Team members can see available actions without memorizing prompts.
- **Consistency:** Everyone uses the same workflow instead of inventing their own prompt phrasing.
- **Auditability:** Because the canvas is code, changes can be reviewed in pull requests.
- **Reuse:** A useful internal tool can be copied from repo to repo or installed from a gist.

Even though the source is a short social post and not formal documentation, the implied architecture is straightforward:

- **Presentation layer:** the canvas UI itself
- **State/data layer:** project metadata about sessions, branches, worktrees, and divergence from main
- **Action layer:** agent-invoked commands such as navigation or cleanup
- **Distribution layer:** repo check-in or gist-based sharing/install

A minimal mental model for a canvas implementation is:

```text
project state -> canvas code renders UI
user clicks UI -> canvas emits action
action -> Copilot agent executes task
updated state -> canvas re-renders
```

For the specific worktree browser example, the central idea is not the visualization alone; it is the combination of visualization and control. The user is not just inspecting branch state, but operating on it from the same surface. That is what makes the feature more powerful than a static dashboard.

The broader takeaway is that Copilot canvases can be used to build thin, task-specific tools for developer ergonomics:

- branch/session browsers
- environment dashboards
- release checklists
- test/runbook control panels
- repo health views
- local cleanup utilities

In all of these cases, the value comes from turning an ad hoc prompt-driven flow into a codified, shareable interface embedded directly in the development assistant.

## Training Exercise

Build a design for your own Copilot canvas before implementing one. The goal is to translate a repetitive workflow into a small in-session UI that combines visibility and action.

### Exercise: Design a "stale branch and worktree manager" canvas

#### Step 1: Pick a real workflow
Choose a workflow you perform repeatedly in a repository, for example:

- checking which feature branches are behind `main`
- identifying orphaned worktrees
- jumping between active task sessions
- finding stale local branches

Write down:

- what data you need to display
- what actions the user should be able to trigger
- what should happen after each action

#### Step 2: Define the data model
Create a small JSON sketch representing the state your canvas would need.

Example:

```json
{
  "project": "my-repo",
  "mainBranch": "main",
  "worktrees": [
    {
      "name": "feature/login",
      "path": "../my-repo-login",
      "sessionId": "sess-123",
      "ahead": 3,
      "behind": 12,
      "changedFiles": 8,
      "orphaned": false
    },
    {
      "name": "feature/cleanup",
      "path": "../my-repo-cleanup",
      "sessionId": null,
      "ahead": 0,
      "behind": 40,
      "changedFiles": 0,
      "orphaned": true
    }
  ]
}
```

#### Step 3: Define the UI behavior
List at least 3 interactions your canvas should support. For example:

1. Toggle sort mode between `ahead/behind` and `changedFiles`
2. Click a worktree to open its Copilot session
3. Click a delete icon on orphaned worktrees to ask the agent to remove them

For each interaction, specify:

- the user event
- the command or prompt sent to the agent
- the expected UI refresh behavior

#### Step 4: Write action prompts
Draft the prompts the canvas would send to Copilot for each action.

Example:

```text
Open the session associated with worktree ../my-repo-login.
```

```text
Delete the orphaned local git worktree at ../my-repo-cleanup and then refresh the session/worktree view.
```

#### Step 5: Version it like a real team artifact
Create a file in your repo such as:

```text
.tools/copilot/stale-worktree-canvas-spec.md
```

Document:

- purpose of the canvas
- required inputs
- supported actions
- team conventions, such as how `main` is identified

#### Step 6: Stretch goal
Generalize your design so it can be shared across repositories. Replace repo-specific assumptions with configuration options like:

- default branch name
- sort metric
- whether destructive actions require confirmation

### What you should learn
By the end, you should be able to:

- identify a workflow suitable for a Copilot canvas
- separate display state from agent-triggered actions
- think about these canvases as team-owned tooling rather than one-off experiments
