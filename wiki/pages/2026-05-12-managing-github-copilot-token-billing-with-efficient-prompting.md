## Overview

These notes cover how GitHub Copilot’s move to token-based billing changes day-to-day usage strategy for developers and engineering teams. Instead of evaluating Copilot only on usefulness, the focus shifts to efficiency: selecting the right model, limiting unnecessary context, compacting long sessions, and requesting tightly scoped outputs.

This matters because token spend is directly affected by prompt size, attached context, session history, and response length. For individual developers, better prompt and context discipline improves value per session. For teams and enterprises, usage observability and governance become necessary to keep adoption productive without letting costs scale faster than value.

## Key Concepts

- **Token-based billing**: Cost depends on how much text is sent to and generated by the model. Prompts, attached code, logs, history, and output length all contribute to spend.
- **Model-task fit**: Simpler tasks usually do not need the most capable or expensive model. Save premium models for deeper reasoning, broader refactors, or multi-file work.
- **Automatic model selection**: Auto selection can choose a model based on task type, policy, and availability, helping avoid overuse of premium models.
- **Context window management**: The context window includes instructions, code, logs, history, and tool output. Keeping it minimal but sufficient reduces waste and improves relevance.
- **Session compaction**: Long-running sessions accumulate history and become more expensive over time. Compaction preserves useful state in a shorter summary.
- **Constrained outputs**: Asking for exact output shapes like “only show the diff” or “3 bullets” reduces token usage and makes responses easier to apply.
- **Usage observability and governance**: Tracking token consumption by workflow, model, or team enables budgeting, guardrails, and better policy decisions.

## How It Works

The main idea is to treat Copilot usage as an optimization problem across three variables: **model choice**, **context size**, and **response size**. In a token-billed environment, every interaction has a cost profile, so efficiency comes from improving the signal-to-token ratio rather than simply reducing usage.

A practical workflow starts with **choosing the least expensive model that can reliably do the job**. For small edits, explanations, formatting, or narrow test generation, a mid-tier or auto-selected model is often enough. Premium models should be reserved for tasks with broader scope or deeper reasoning needs, such as architectural tradeoffs or coordinated changes across multiple files.

The next major lever is **context control**. In Copilot and Copilot CLI, context may include system instructions, past chat turns, attached files, pasted snippets, logs, stack traces, and command output. The notes highlight `/context` as a way to inspect how that window is being used. The important practice is to include only what the current task needs: the relevant function, diff, stack trace, or requirement. Sending a whole file or repository for a local issue is usually wasteful.

Long sessions create a second-order cost problem because earlier turns may be repeatedly carried forward. That is where **session compaction** helps. If supported, Copilot CLI can compact automatically near token limits, and `/compact` can be run manually. This keeps the assistant useful while replacing a long transcript with a concise summary of the important state.

Another effective tactic is **output constraint**. Broad prompts tend to produce long explanations, which increases generation cost and review effort. Tight instructions such as the following improve both efficiency and workflow:

```text
Only show the diff.
No explanation.
Return only the changed function.
Summarize in 5 bullets.
Give me a one-paragraph root cause.
```

The notes also emphasize **measurement**. Commands like `/usage` make it possible to compare workflows and identify costly patterns, such as broad prompts, oversized attachments, overuse of premium models, or long sessions without compaction. At team scale, that data supports governance decisions such as default model policies, budget allocation, quota design, and training.

A practical operating model from the notes:

1. Default to Auto model selection or a mid-cost model.
2. Escalate to premium models only when deeper reasoning is clearly needed.
3. Scope prompts to the smallest relevant code unit.
4. Use `/context` to inspect context bloat.
5. Use `/compact` during long sessions.
6. Ask for tightly constrained output.
7. Review `/usage` regularly to identify expensive workflows.
