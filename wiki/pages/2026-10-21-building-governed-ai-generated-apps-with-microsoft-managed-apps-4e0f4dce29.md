## TL;DR

> Microsoft Managed Apps provides a governed runtime for AI-generated applications, combining flexible code generation with Microsoft authentication, connectors, DLP policies, and administration. The practical lesson is to plan carefully, keep the project under source control, let an AI agent build and test it, and then perform human security and usability reviews.

## Key Takeaways

1. Publish AI-generated applications into a managed environment when organizational authentication, connector controls, DLP policies, consumption visibility, and administration matter.
2. Start with a detailed implementation prompt that specifies the managed runtime, data source, site or environment, required workflows, interface behavior, and sample records.
3. Use a private GitHub repository and source control so changes remain compartmentalized and can be reviewed or rolled back.
4. Separate inexpensive planning from metered building: refine requirements before starting an agent workflow that consumes credits.
5. Let browser automation test functionality and responsive layouts, but manually inspect visual details, permissions, labels, and domain behavior that automated tests can miss.
6. SharePoint permissions must be granted separately from app access; sharing the app link alone does not grant access to its underlying lists.
7. The presenter reports spending about 40 minutes and $3.70 in total to generate, test, repair, and populate the demonstrated inventory app, while noting that costs depend on credits, licensing, and agent activity.

## Overview

Microsoft Managed Apps, presented here as a preview capability, provides a destination for code-based applications generated with tools such as GitHub Copilot, Copilot Studio, Copilot Cowork, Claude, or OpenAI tools. The example is a React inventory application backed by six SharePoint lists and accessed with Microsoft identities.

The approach matters to organizations that want faster AI-assisted development without creating an unmanaged collection of internet-hosted apps. Makers, Power Platform professionals, administrators, and security teams should care because application generation remains flexible while deployment, identity, connectors, policies, sharing, and consumption stay within Microsoft’s managed infrastructure.

## Key Concepts

- **Managed application runtime**: The demonstrated application is a code app written in React and published into Microsoft’s managed infrastructure. It does not expose the familiar visual studio or Edit button; changes are made through the source project and development agent.
- **Governed AI development**: The application may be generated by various AI coding tools, but its runtime remains subject to Power Platform controls. The presenter highlights authentication, connectors, DLP policies, administration, and consumption visibility as the main benefits over independently hosted applications.
- **Prompt as implementation specification**: A useful build prompt goes beyond naming an app. It should identify the target managed runtime, SharePoint site and list naming, required records and workflows, design expectations, drag-and-drop behavior, sharing features, activity tracking, and desirable enhancements.
- **Planning before metered execution**: The presenter first uses an included Copilot experience to discuss requirements and assemble one comprehensive prompt. Only then does he submit it to the credit-consuming GitHub Copilot workflow, reducing the risk of paying for an extended build on a poor foundation.
- **Source control and reusable project knowledge**: A private GitHub repository provides version history, rollback options, and separation between projects. After a complex earlier build, the presenter also asked the agent to create a Markdown guide containing lessons such as runtime customization and tool-specific practices, then supplied that guide to later sessions.
- **Agent-driven browser testing**: GitHub Copilot uses browser automation to create or inspect resources, exercise the app, test responsive layouts, and fix defects. This can consume most of the elapsed time and credits, so the presenter sometimes disables repeated automated validation for small changes that he intends to verify manually.
- **Layered access control**: Application sharing and data authorization are distinct. A SharePoint-backed app requires users to have access both to the managed app and to the relevant SharePoint lists; a Dataverse-backed app similarly depends on Dataverse permissions.
- **Licensing and consumption**: The presenter reports that his Power Apps Premium license covered the demonstrated runtime without additional credits for his own use. He says users without suitable licensing may consume credits, as may additional services such as Work IQ or usage beyond included allowances; exact costs therefore depend on the environment and workload.

## How It Works

1. Review Microsoft’s quick-start documentation and have the coding agent install and verify the required tooling; restart the CLI session afterward if instructed.
2. Create a private GitHub repository so generated code and subsequent changes are versioned.
3. Discuss the application with a planning assistant before starting metered work. Specify the managed runtime, data source, environment, user workflows, interface expectations, and security assumptions.
4. Convert those requirements into one comprehensive prompt and explicitly identify the intended Microsoft managed-app runtime so the agent does not select a different meaning of “managed app.”
5. Submit the prompt to the development agent, answer clarification and authentication questions, and review its implementation plan before approving the build.
6. Let the agent create the data structures, generate the React application, connect authentication and data, publish it, and run browser-based functional and responsive tests.
7. Inspect the result manually. Provide screenshots and precise descriptions for visual defects, then ask for focused repairs.
8. Add representative sample data and test real workflows such as editing records and moving items on a status board.
9. Configure app sharing and separately grant access to the underlying SharePoint or Dataverse data. Confirm that organizational DLP policies permit every connector used.
10. Review licensing, credit consumption, security roles, usability, and governance before treating the preview-based application as production-ready.

## Training Exercise

1. Define a small inventory scenario with three workflows: create an asset, edit its status, and move it between status columns.
2. Write a structured specification containing the target managed-app runtime, a private repository, the SharePoint site and list prefix, required fields, user experience, responsive behavior, authentication, and sample data.
3. Ask a planning assistant to find ambiguity in the specification and consolidate it into one build prompt before starting any metered agent run.
4. Have the development agent present its implementation plan. Check that it covers data structures, application screens, validation, deployment, and testing before approving it.
5. After generation, test desktop and narrow mobile layouts. Inspect field borders, labels, empty states, editing, drag-and-drop behavior, and error handling rather than relying solely on automated checks.
6. Report one defect with a screenshot and a precise reproduction description, then request a narrowly scoped fix.
7. Create about a dozen varied sample records and exercise the complete workflow.
8. Document an access matrix showing who can open the app, who can access its underlying lists, and which DLP policies affect its connectors.
9. Record elapsed time, reported credit cost, defects caught automatically, and defects caught manually. Use those observations to create a short reusable Markdown guide for the next build.

## Test Yourself

<details><summary>Why is a managed runtime preferable to publishing an AI-generated app directly on an arbitrary public host?</summary>

The managed runtime preserves organizational controls such as Microsoft authentication, DLP policies, connector governance, administration, and consumption visibility. It gives teams freedom to generate code with different tools without abandoning centralized security and management.

</details>

<details><summary>Why should requirements be refined before asking the development agent to build?</summary>

Agent construction and testing consume credits, so an ambiguous prompt can spend money while following the wrong path. Planning first also produces a clearer specification covering data, workflows, interface behavior, security, and deployment.

</details>

<details><summary>Why does successful automated testing not mean the application is ready for organizational use?</summary>

In the demonstration, browser automation exercised functionality and responsive layouts but missed clipped field borders, a missing letter in a label, and another interaction defect. A person must still validate visual quality, business behavior, sharing rules, underlying data permissions, and DLP compliance.

</details>
