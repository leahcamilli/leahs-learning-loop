## TL;DR

> Use a fast “System 1” model as a typed, probabilistic if-statement for narrow classification and routing—not for tasks that require reasoning or synthesis. This separation can make high-volume automation faster and cheaper while keeping state, policy, and escalation under deterministic program control.

## Key Takeaways

1. Treat schema conformance and decision quality as separate properties: valid JSON prevents interface failures but does not make a classification correct.
2. Put deterministic code in charge of workflow state and policy; use the classifier only to return labels, scores, confidence values, or routing decisions.
3. Automate low-risk cases only above thresholds calibrated on representative labeled data, and escalate ambiguous or high-impact cases to a reasoning model or human.
4. Use fast classifiers for categorization, ranking, moderation, filtering, and routing—not code generation, context compaction, long-running planning, or complex output judging.
5. Preserve continuity outside the model: the source’s game demos oscillated when each frame produced a stateless decision without prior intent.
6. The source reports roughly 70–500 ms responses, about $0.04 per million input tokens, free output tokens, and zero structured-output errors in provider evaluations; independently test these claims on the production workload.
7. Evaluate schema validity, semantic accuracy, calibration, latency, cost, throughput, false-positive impact, and escalation rate independently.

## Overview

This lesson explains how a specialized “System 1” model such as Jev can serve as a fast classification and routing function inside software. Unlike a general-purpose language model, it is presented as optimizing for immediate, structured decisions: application state goes in, and schema-conforming JSON with scores or confidence values comes out. The source reports very low latency, low input-token pricing, free output tokens, and zero structured-output format errors in the provider’s evaluations, but it also notes that the underlying benchmarks were not published and that some reference answers were generated by other models. Treat those performance figures as reported claims rather than independently established facts. The practical design rule is to use this kind of model for classification, ranking, moderation, filtering, and routing—not for code generation, context compaction, long-running planning, or judgments requiring substantial reasoning.

## Key Concepts

- **System 1 versus System 2 tasks**: System 1 tasks are fast judgments that require little deliberation, such as labeling an email, identifying a topic, or choosing a route from a small set of actions. System 2 tasks require reasoning, synthesis, planning, or investigation. The source positions Jev for the former and general-purpose reasoning models for the latter. A useful heuristic from the video is to ask whether a person could decide almost immediately after perceiving all relevant information.
- **Typed structured output**: The model accepts an output schema and returns data in that shape, making it easier to integrate with ordinary programs. The source distinguishes deterministic structure from nondeterministic content: the JSON shape can be guaranteed even though the selected label, score, or action can still vary or be wrong. Type safety therefore prevents malformed interfaces; it does not guarantee semantic truth.
- **The smart if-statement pattern**: A specialized classifier works well as a probabilistic branch in a larger deterministic workflow. Code collects state, the model assigns labels or scores, and ordinary logic decides what happens next. Examples include routing an alert, prioritizing email, categorizing videos, selecting a webpage link, or sending uncertain cases to a stronger model or a human.
- **Confidence-based automation**: Scores and confidence estimates let a system establish thresholds instead of treating every prediction equally. High-confidence cases can be automated, ambiguous cases can be escalated, and threshold changes can trade coverage for reliability. Confidence still needs calibration against labeled examples; merely returning a number does not prove that the number accurately represents error probability.
- **Latency, cost, and parallel classification**: The source reports responses in roughly 70–500 milliseconds for relevant tasks, input pricing around four cents per million tokens, free output tokens, and support for processing many inputs in parallel. It also describes an email experiment averaging about 200 milliseconds per email with eight workers. These properties can make previously uneconomical high-volume classifications practical, although production measurements should be repeated on the actual workload.
- **Stateless decisions and limited context**: The model is described as receiving current structured state rather than maintaining a rich history or reasoning trace. In game demonstrations, repeatedly deciding from each new frame caused oscillating behavior because prior intent was not preserved. The source also reports a 32k-token context window. Applications that need continuity should maintain state explicitly in code and pass only the relevant state into each classification.
- **Poor fits and failure boundaries**: The source warns against using a fast classifier to judge complex model outputs, generate code or prose, perform context compaction, or make decisions requiring codebase exploration and extended reasoning. Context compaction is synthesis rather than simple filtering; deleting earlier history can also invalidate caches, omit tool results, lose reasoning-related context, or remove information needed later. Cheap, fast execution does not compensate for using the wrong cognitive capability.
- **Evidence and evaluation discipline**: Claims about exceptional speed, cost, and schema reliability should be separated from claims about decision quality. The source says the provider did not publish the benchmark used for some comparisons and used outputs from other models as reference answers, which may themselves be imperfect. A responsible evaluation therefore measures schema validity, task accuracy, calibration, latency, cost, and escalation rate independently.

## How It Works

Define a narrow decision contract, such as an email category, a confidence score, and an escalation flag. Convert the relevant application state into compact text or structured data, then call the classifier with the required schema. Validate the response at the program boundary even if the service promises schema conformance. Apply explicit policy in normal code—for example, archive obvious spam above a tested threshold, forward uncertain messages to a reasoning model, and require human review for high-impact actions. Preserve workflow state outside the model so each call can include prior actions when continuity matters. Before deployment, evaluate the complete pipeline on representative labeled data and record semantic accuracy, false-positive costs, confidence calibration, tail latency, throughput, and cost. The main architectural separation is simple: deterministic code owns state and policy, the fast model supplies probabilistic classifications, and stronger reasoning systems handle genuinely deliberative cases.

## Training Exercise

Build a three-stage email triage prototype. First, define a fixed schema containing category (spam, transactional, personal, work, or uncertain), confidence from 0 to 1, urgency from 0 to 1, and requires_review as a boolean. Second, prepare at least 50 representative, manually labeled messages, including ambiguous and adversarial examples. Third, classify them and measure schema-validity rate, per-category precision and recall, latency, and whether confidence aligns with actual accuracy. Create routing rules that automatically handle only low-risk, high-confidence messages; send uncertain cases to a general-purpose reasoning model or a human. Repeat the evaluation at several confidence thresholds and document the coverage-versus-error tradeoff. Finally, identify five messages that require synthesis, external context, or multi-step reasoning and explain why the fast classifier should escalate them instead of deciding alone.

<details><summary>Why does typed structured output not guarantee a correct decision?</summary>

The schema can guarantee fields and data types, but the selected label, score, or action remains probabilistic. Type safety prevents malformed interfaces, not semantic mistakes.

</details>

<details><summary>How should a production pipeline divide responsibility among code, a System 1 classifier, and stronger decision-makers?</summary>

Code should own state, validation, thresholds, and policy; the classifier should provide narrow probabilistic judgments. Uncertain or consequential cases should be escalated to a reasoning model or human.

</details>

<details><summary>What should be measured before automating decisions with a fast classifier?</summary>
