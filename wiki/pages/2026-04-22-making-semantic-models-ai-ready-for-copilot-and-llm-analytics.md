## TL;DR

> Reliable LLM analytics starts with a sound, explicit semantic model—not better prompting alone. Clean structure, approved measures, concise metadata, grounding anchors, and canonical examples give AI tools the context needed to select the right logic and avoid plausible but incorrect answers.

## Key Takeaways

1. Fix source data, relationships, DAX, performance, and security before adding Copilot or data agents; AI cannot compensate for a broken semantic model.
2. Use a star schema, clear business names, proper date tables, numeric data types, and explicit semantic-model measures so both people and LLMs can interpret the model consistently.
3. Reduce context noise by hiding or removing foreign keys, duplicate attributes, legacy measures, unused history, unnecessary MDX exposure, and fields users should not query directly.
4. Document ambiguity rather than everything: add concise descriptions, real business synonyms, and short AI instructions that define defaults and require reuse of approved measures.
5. Treat context as finite; verbose, redundant, or autogenerated metadata can create context rot and make the correct model objects harder for an LLM to identify.
6. Add grounding anchors such as verified totals, directional constraints, edge-case rules, and known-correct answers so agents can detect drift before errors compound.
7. Provide canonical prompt-to-query pairs and approved DAX patterns—including required query structure and preferred conventions—to discourage invented logic.

## Overview

These notes summarize how to prepare a Power BI or Fabric semantic model so LLM-powered tools such as Copilot, data agents, and coding assistants can query it accurately. The main idea is that good AI output depends not just on prompts, but on the quality of the underlying model: its structure, naming, metadata, examples, and explicit business logic.

This matters because AI systems magnify both good and bad modeling practices. A clean star schema, explicit measures, concise descriptions, and carefully chosen instructions help both humans and machines reason correctly. Ambiguous names, hidden business definitions, noisy schemas, and implicit calculations increase the risk of hallucinations, wrong metric selection, and wasted context.

## Key Concepts

- **AI readiness as context engineering**: LLM performance depends on the prompt plus all visible schema, metadata, instructions, and examples. Preparing a semantic model for AI means making the right information explicit while minimizing noise.
- **Structural foundation first**: AI cannot fix broken relationships, incorrect DAX, poor data quality, or weak security. Classic BI discipline remains the prerequisite for trustworthy AI-assisted analytics.
- **Star schema and explicit modeling**: Star schemas are easier for both humans and LLMs to interpret. Important metrics should be defined as explicit semantic model measures rather than relying on implicit or report-scoped logic.
- **Finite context budget**: More documentation is not always better. Concise, targeted metadata usually works better than verbose or redundant descriptions that create “context rot.”
- **Annotations as behavior guidance**: Descriptions, synonyms, AI instructions, inline comments, and external links can encode business meaning, edge cases, and preferred behaviors that structure alone cannot express.
- **Grounding anchors and examples**: Known-correct values, business rules, and canonical examples help agents validate outputs and follow approved modeling patterns instead of inventing logic.

## How It Works

The lesson frames AI readiness as a progression from standard semantic-model quality to AI-specific context design.

Start with actual user needs before enabling Copilot or data agents. Identify who will use natural-language access, what questions they ask, and whether the semantic model already contains the approved measures needed to answer those questions. Without this step, AI may generate plausible but nonstandard DAX for concepts that should have been explicitly modeled.

Next, confirm the model is fundamentally sound. Trustworthy source data, correct relationships, strong DAX, acceptable performance, and correct security are non-negotiable. If business logic exists only in analysts’ heads or report-specific workarounds, AI has no dependable basis for reasoning.

Then reduce schema noise. Every unnecessary table, column, duplicated attribute, and legacy measure increases the chance an LLM chooses the wrong object. Useful cleanup actions include hiding or removing foreign keys in fact tables, avoiding duplicated descriptive fields, trimming unused history, disabling Auto Date/Time, using proper date tables, storing numerics as numeric types, and limiting unnecessary MDX exposure. This improves both model efficiency and AI navigation.

After the basics, add AI-specific context through four levers:

1. **Structure**  
   Use clear business naming, expose explicit measures, hide fields users should never reference directly, and prefer star-schema layouts. Explicit semantic-model measures are especially important because implicit measures and report-scoped measures are unreliable for many AI consumers.

2. **Annotations and documentation**  
   Add concise descriptions where ambiguity exists, not everywhere. Use AI instructions for organization-specific rules such as defaulting “margin” to a specific approved metric or requiring agents to prefer existing measures over ad hoc DAX. Synonyms should reflect actual business language, and external links may be better than copying long documentation into the model. Avoid low-value autogenerated descriptions that add no new meaning.

3. **Grounding anchors**  
   Give agents checkpoints: known totals, directional constraints, edge-case rules, and verified answers for fragile query types. These act as truth references that help detect drift before an incorrect intermediate result compounds into a worse answer.

4. **Examples**  
   Provide canonical measures, approved prompt-to-query pairs, and standard DAX patterns. Examples teach both syntax and conventions, such as the required `EVALUATE` structure in DAX queries or the preferred `VAR/RETURN` style for time intelligence.

A practical takeaway is that AI readiness is mostly strong semantic-model hygiene plus careful context design. Humans can often compensate for ambiguity with experience; LLMs generally cannot. The more institutional knowledge is encoded clearly in the model, the more reliable AI-assisted analysis becomes.

The training exercise in the notes turns this into a repeatable review process: inventory objects, remove noise, convert one metric to an explicit measure, improve naming and descriptions, add a short AI instruction block, define grounding anchors, and test with natural-language prompts. This is a useful checklist before exposing any semantic model to Copilot or agent-driven querying.

Overview

This lesson explains how to prepare a semantic model so large language models (LLMs) such as Power BI Copilot, Fabric data agents, and coding assistants can query it accurately and consistently. The article’s core argument is that prompt quality is only one part of the equation: output quality also depends heavily on model structure, metadata, grounding information, and examples that constrain the model’s behavior.

This matters to analytics engineers, BI developers, and semantic model owners because AI tools amplify both strengths and weaknesses in a model. Clean naming, explicit measures, strong star-schema design, concise descriptions, and curated instructions improve outcomes for both human analysts and AI systems. The same work that reduces ambiguity for a new teammate also reduces hallucinations and wasted tokens for an LLM.

Key Concepts

  *   AI readiness as context engineering: An LLM does not answer from the prompt alone; it answers from the prompt plus whatever model metadata, instructions, examples, and accessible schema it can see. Preparing a semantic model for AI is therefore a context-engineering exercise: make important information explicit, remove noise, and give the agent enough signal to reason correctly without overwhelming it.
  *   Structural foundation: Accurate data, a functional semantic model, correct DAX, and proper security remain the prerequisites for any analysis workflow. AI does not compensate for broken relationships, ambiguous filters, poor calculations, or misconfigured permissions; it often makes those weaknesses more visible and more costly.
  *   Star schema and explicit modeling: A star schema is both a best practice for analytics performance and a pattern that LLMs are more likely to interpret correctly. Explicit measures are especially important because Copilot and data agents cannot reliably use implicit measures or report-scoped measures when querying the semantic model directly.
  *   Context budget: Context is finite, so more metadata is not always better. Verbose, redundant, or conflicting descriptions can create 'context rot,' where relevant facts are drowned out by excess detail; concise, targeted metadata tends to produce better AI behavior than large amounts of generic documentation.
  *   Annotations and behavior guidance: Descriptions, synonyms, AI instructions, inline DAX comments, and links to external documentation help encode meaning that structure alone cannot express. These mechanisms are most valuable when they capture organization-specific definitions, edge cases, and behavior rules such as preferring existing measures over ad hoc calculations.
  *   Grounding anchors and examples: Grounding anchors are known-correct values or rules that let an agent verify its own output instead of compounding mistakes. Examples such as canonical measures, prompt-to-query pairs, and edge-case patterns show the LLM what 'correct' looks like in your organization’s modeling conventions.

How It Works

The article lays out AI readiness as a four-step progression from classic BI discipline to AI-specific context design.

First, start with user needs, not tooling. Before enabling Copilot or data agents, identify who wants natural-language access, what kinds of questions they ask, how many users will actually adopt the experience, and what training or change management they need. This matters because conversational BI often invites users to ask questions outside the semantic model’s scope. If the model lacks a defined measure, AI tools may generate ad hoc DAX that appears plausible but does not align with organizational standards.

Second, ensure the semantic model is fundamentally sound:

- **Data quality** must be trustworthy end to end. - **Model design** should avoid ambiguity and ideally follow a star schema. - **DAX logic** must return correct values and perform acceptably. - **Security** must be configured so AI-enabled access does not expose the wrong data.

These are not AI-specific concerns, but they are prerequisites. If revenue logic is implicit in analysts’ heads instead of encoded in the model, the LLM has no reliable way to infer it.

Third, optimize the model so both humans and LLMs can navigate it efficiently. The article emphasizes reducing clutter because every extra table, column, and redundant field increases the chance that an LLM selects the wrong object. Practical actions include:

- Remove unused tables and columns. - Avoid redundant fields where a dimension already contains the canonical attribute. - Filter out unnecessary rows and overlong history. - Aggregate away detail that does not support analysis. - Disable Auto Date/Time and use a proper date table. - Reduce decimal precision
